# DashGuard frontend

Phone-first, warm and calm web app built with plain HTML, CSS and JavaScript. The live camera detector uses the pinned MediaPipe Tasks Vision Web runtime in a Web Worker.

## Run locally

From this directory:

```bash
python -m http.server 8080
```

Open http://localhost:8080. Installability and offline caching require serving from localhost or HTTPS. The service worker caches the UI shell, including the motion-monitor module, after the first load.

## Screens

- Home: camera-view illustration, drive snapshot and Start Drive.
- Drive: preview overlay, alert status, live phone motion monitor, rolling jerk graph, timer and End Drive.
- Events: local saved-event placeholder.
- Settings: voice preference, pre-event duration and offline status.

## Live motion monitor

The Drive screen now reads browser `DeviceMotionEvent` data after the user taps **Enable Motion**. It plots a rolling 20-second jerk trace, displays linear acceleration, and displays gyroscope rotation rate when the browser provides it.

- Serve from HTTPS or localhost. Browsers generally restrict motion sensors on insecure origins.
- iOS browsers that require motion permission show the native permission prompt after the user taps the button.
- Some browsers/devices may not provide linear acceleration or gyroscope fields. A gravity-compensated fallback is used for acceleration when possible; missing gyroscope data is shown as unavailable.
- The motion monitor runs while the page is active. It is not a background sensor service.
- The displayed high-jerk marker uses a prototype threshold and is **not calibrated, validated, or connected to automatic event capture**.

## Live camera preview

Drive Mode now requests a live video preview when **Start Drive** is tapped. It prefers the rear-facing camera, requests video only (no microphone), and places the stream directly in the Drive screen. Use **Stop Camera** to release it without ending Drive Mode. Leaving the Drive screen or ending Drive Mode also stops every camera track.

- Camera access requires a secure context: use HTTPS or localhost. The browser will ask for camera permission.
- Rear-camera selection is a preference, not a guarantee on every device/browser.
- The preview is foreground-only and is **not recording or saving video**. Local object detection starts automatically on the same camera stream when the detector has loaded.
- If permission is denied, the camera is unavailable, or another app is using it, the Drive screen shows an error and allows a retry.
- The native camera indicator remains controlled by the operating system/browser.

## Run motion-monitor tests

From this directory, with Node.js installed:

```bash
node --test tests/*.test.cjs
```

The tests cover linear-acceleration readings, jerk calculation, the gravity-compensated fallback, gyroscope readings, denied permission, and missing sensor data. They use mocked browser events; they do not replace testing on a physical phone.

## Live object detection

The Drive screen runs Google's EfficientDet-Lite0 object detector through MediaPipe Tasks Vision 1.2.3 in a dedicated classic Web Worker. The worker dynamically imports the ESM vision bundle but remains a classic worker so MediaPipe can load its WASM glue with `importScripts`; module workers do not support that API. It analyses frames from the existing camera preview stream and draws real boxes and confidence labels over that same video. No second camera session is opened. The model recognises common COCO categories; DashGuard displays faces, people, bicycles, cars, motorcycles, buses, trains, trucks, traffic lights, stop signs and parking meters. A dedicated MediaPipe BlazeFace full-range detector runs beside the COCO object detector on the same camera frame, so a face gets its own `FACE` box rather than relying on the `person` category. The detector is throttled to roughly 5–6 frames per second to limit phone load.

The runtime and models are fetched on first use and cached by the service worker where the browser permits. Cache warming is best-effort: a cache quota or optional face-model failure must not block road-object detection. Connect once before expecting offline detection. Clearing site data removes those cached assets. Startup errors now identify whether the JavaScript runtime, WebAssembly runtime, or required road-object model failed to load. MediaPipe performs image inference on-device and does not send camera frames to Google, though the SDK may send usage metrics as described in its privacy notice. The model and runtime are not bundled in the source repository.

Face boxes are generated by BlazeFace full-range, selected for back-camera footage. DashGuard still defaults to the rear camera for road monitoring: your own face will only be boxed if it is actually visible in that camera's preview. For a quick self-test, use a webcam or aim the active camera at a face.

The browser now assigns short-lived session IDs to detections using a lightweight IoU + predicted-center association tracker. IDs persist across nearby frames and brief missed detections, then expire after the configured miss/time limit. This is geometric tracking, not learned re-identification: IDs can switch when objects overlap, cross, disappear for too long or the detector misses them. Detection speed and quality depend on the phone and browser and must be tested on-device. This is not a driving safety system.

## Not connected yet

Distance/TTC estimation, audio safety alerts, video recording, 60-second pre-event buffering and protected event clips are not implemented. Browser camera and sensor access remain foreground-only.

Browser camera and motion access are foreground features. DashGuard stops the camera when you leave Drive Mode, and a browser may suspend capture when the tab is backgrounded or the phone is locked. The web version will not claim to be a dependable background dashcam; any future recording feature must clearly show when capture is active and handle browser interruptions.


## Object-detection tests

The detection-controller tests use a mocked worker, face-result normalization and canvas geometry; they do not test real model accuracy or frame rate. Real detection requires HTTPS or localhost, a supported modern browser, camera permission and a first online model/runtime load.


## Object tracking

Every detection is associated with an ephemeral track ID (`#1`, `#2`, ...) using class-consistent bounding-box IoU and predicted center movement. Matching is greedy one-to-one, motion-smoothed and bounded to a short missed-frame window. IDs reset when detection stops or Drive Mode ends. The tracker is a lightweight geometry heuristic and has not been validated on road footage; it is not a multi-object tracking benchmark implementation.
